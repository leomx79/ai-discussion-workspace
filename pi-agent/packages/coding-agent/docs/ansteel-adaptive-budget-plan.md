# Ansteel 自适应证据预算方案

## 1. 问题

当前 Ansteel 审查为每个阶段和整个项目设置固定限制：

- `stageTimeoutMs`
- `maxStageTimeoutMs`
- `maxToolCallsPerStage`
- `maxProjectToolCalls`
- `projectTimeoutMs`

这些限制能够阻止无限运行，但不能判断角色是否正在取得有效进展。初始泛查可能耗尽共享工具额度，后续修订、验证或最终会签却缺少必要证据；反过来，角色也可能重复搜索或触发受限请求，却获得额外时间。

目标是让协调器依据不可变、可审计的证据进展动态分配时间和工具，而不是由模型自行声明“还需要预算”。

## 2. 目标

1. 保留时间、工具、角色、修订轮数和审查范围的硬性 fail-closed 上限。
2. 将稀缺预算优先分配给未完成的治理工作，特别是修订、验证和最终会签。
3. 只奖励协调器观察到的新证据，绝不奖励模型自己的文字声明。
4. 对重复、被拒绝、越界、排除路径和无新证据请求施加惩罚。
5. 将每次授予、拒绝和原因写入 Markdown 报告和运行检查点。
6. 策略必须确定性、可测试，不能依赖真实提供商才能验证。

## 3. 非目标

- 模型不能自行设定或扩大预算。
- 超时延长不等同于批准。
- 不扩大审查根目录，不允许 shell，不允许将生成的 Ansteel 状态作为证据。
- 不把提供商失败当作证据进展而重试。
- 不隐藏预算拒绝；拒绝必须成为可审计的治理事件。

## 4. 协调器状态

协调器维护不可变的 `AdaptiveBudgetState`：

```ts
interface AdaptiveBudgetState {
  projectStartedAt: number;
  hardProjectDeadline: number;
  remainingProjectToolCalls: number;
  remainingProjectTimeMs: number;
  stage: AnsteelDiscussionStage;
  role: AnsteelRole;
  stageBaseTimeoutMs: number;
  stageGrantedTimeoutMs: number;
  stageHardTimeoutMs: number;
  stageBaseToolCalls: number;
  stageGrantedToolCalls: number;
  stageHardToolCalls: number;
  evidenceProgressCount: number;
  duplicateOperationCount: number;
  blockedRequestCount: number;
  unresolvedChallengeCount: number;
  allocationEvents: AdaptiveBudgetEvent[];
}
```

该状态只能从协调器时间戳、阶段审计事件、不可变证据包、问题台账和工具操作哈希导出，不能由角色回答拼接而成。

## 5. 什么是证据进展

一次事件只有同时满足以下条件才记为证据进展：

1. 工具执行成功。
2. 依据规范化工具操作哈希，它在本次审查中是新的操作。
3. 目标仍在已解析审查根目录内，且不属于排除的协调器状态。
4. 当前阶段仍缺少必要产出：工作卡、分配问题的回应、验证裁决或最终会签。

以下情况不计入进展：

- 被拒绝的请求，包括 `..`、排除的 Ansteel 状态和 shell；
- 重复操作哈希；
- 失败的工具执行；
- 必要阶段回答已完成后的请求；
- 提供商重试、格式修复或模型文字主张。

## 6. 分配策略

### 6.1 初始额度

协调器为每个阶段给出保守的初始额度。初始调查获得最少份额，修订、验证和会签保留受保护预算。

| 阶段类别 | 初始时间 | 初始工具 | 是否可延展 |
| --- | ---: | ---: | --- |
| 初始工作卡 | 120 秒 | 8 | 最多一次 |
| 交叉质询 | 90 秒 | 0 | 否 |
| 修订 | 180 秒 | 12 | 最多两次 |
| 验证 | 150 秒 | 8 | 最多一次 |
| 最终会签 | 90 秒 | 2 | 否 |

全局配置的硬上限仍然最高优先级。阶段初始额度不得超过阶段类别上限、剩余项目预算或硬截止时间。

### 6.2 时间续配

在软超时时，协调器只有同时满足以下条件才授予一次小额度续配：

1. 该角色自上次预算决定后至少产生一个新证据进展事件。
2. 当前阶段仍缺少有效的必要回答。
3. 角色没有超过被拒绝请求或重复请求阈值。
4. 后续强制阶段的受保护预算仍然充足。
5. 项目硬截止时间和阶段硬上限允许本次续配。

每次续配应很小且明确，例如 30 秒；它绝不是重新开始阶段计时。

### 6.3 工具续配

角色耗尽初始工具额度后，协调器仅在新证据能直接回应未关闭问题或补足必要工作卡断言时，授予一个小工具批次。

下列情况必须拒绝工具续配：

- 请求模式重复或被拒绝；
- 当前必要产出已具备足够不可变证据；
- 续配会侵占验证或会签的受保护预算；
- 项目工具硬上限已到达。

被拒绝请求占用小型反循环额度，但绝不能成为获得额外工具的理由，也不能扩大审查范围。

### 6.4 受保护预算

在给初始工作卡阶段授予可选续配前，协调器必须预留以下预算：

- 三个交叉质询；
- 有开放问题时至少一轮完整修订；
- Staff Engineer 和 QA Engineer 的独立验证；
- 形成共识后的两次最终会签。

若无法保证这些强制门禁，必须拒绝可选的初始阶段续配，要求角色基于现有证据给出结论。此时可以 fail-closed 拒绝，但不能让初始泛查饿死后续治理阶段。

## 7. 预算账本

将不可变 `AdaptiveBudgetEvent` 写入报告和检查点：

```ts
interface AdaptiveBudgetEvent {
  role: AnsteelRole;
  stage: AnsteelDiscussionStage;
  action: "grant-time" | "grant-tools" | "deny-time" | "deny-tools" | "penalize-blocked" | "penalize-duplicate";
  requested?: { timeMs?: number; toolCalls?: number };
  granted?: { timeMs?: number; toolCalls?: number };
  evidenceProgressCount: number;
  unresolvedChallengeCount: number;
  remainingProjectTimeMs: number;
  remainingProjectToolCalls: number;
  reason: string;
}
```

报告必须在转录前包含 `## Adaptive Budget Ledger`。该节必须声明所有计数均由协调器导出，并按时间顺序展示每次预算决定；角色文本不能覆盖该账本。

## 8. 配置

新增可选的 `adaptiveBudgetPolicy`。省略它时，保留当前固定预算行为以确保兼容性。

```json
{
  "adaptiveBudgetPolicy": {
    "enabled": true,
    "projectTimeoutMs": 900000,
    "maxProjectToolCalls": 96,
    "timeExtensionMs": 30000,
    "toolExtensionCalls": 4,
    "maxBlockedRequestsPerStage": 2,
    "maxDuplicateRequestsPerStage": 2,
    "protectedVerificationTimeMs": 360000,
    "protectedVerificationToolCalls": 24
  }
}
```

校验要求：

- 所有值都是有界的正整数；
- 受保护预算必须能放入项目上限；
- 策略不能突破已有绝对最大时间或工具常量；
- `enabled: false` 等价于省略该策略；
- 非法策略必须在创建任何角色会话前拒绝。

## 9. 长任务与可恢复执行

实际工程审查可能跨越数小时。不能仅把 `projectTimeoutMs` 提高到数小时：那会让一个前台 CLI 进程、网络连接和模型调用持续悬挂，进程崩溃、网络重连或桌面退出时都难以恢复。

应将长任务建模为多个短的、可审计的执行批次（epoch）：

1. 单次提供商调用仍使用分钟级硬超时，建议 1 到 5 分钟；单次调用超时不能无限等待。
2. 一个 epoch 只运行有限的阶段工作，例如 5 到 10 分钟、一个阶段软上限或一个有界工具批次。
3. epoch 到达边界时，协调器保存检查点并停止当前进程；它不是整体审查失败。
4. 本地 `pi --ansteel-supervise` 监督器从检查点的下一个合法状态转换继续：它为每个 epoch 启动独立短生命周期子进程，重新建立短连接，而不是恢复旧网络连接或让模型重写历史。显式 `pi --ansteel-resume <run-id>` 仍用于监督器停止后的手动恢复。
5. 项目级 SLA 可以是数小时，例如 4 小时，但它是多个 epoch 的累计截止时间，而非一次连续的模型调用。

检查点必须额外持久化：

- 不可变证据包及其哈希；
- 首次 epoch 选中的证据文件相对路径清单，以及当时的候选文件总数；恢复时只重建这一份冻结清单，新增但未入选的普通文件不能挤掉旧文件或制造伪变更；
- 已完成阶段、角色响应、问题台账和预算账本；
- 下一个唯一合法动作、当前 epoch 编号、原始项目起点和累计项目硬截止时间；恢复不得以新进程启动时间重算 SLA；
- 角色 `provider/model` 身份及其变更历史；
- `ready-to-resume`、`waiting-provider`、`blocked`、`expired`、`completed` 等协调器状态。

恢复前必须重新校验检查点版本、证据包哈希、角色身份、配置预算和状态转换合法性。累计项目硬截止时间已经过去时，恢复必须在调用任何角色前以 `expired` 归档。冻结清单中的文件被修改、删除、变成不可读或越界时，重建哈希必须变化并拒绝恢复；新建但未被首次快照选中的普通文件不属于已承诺的证据边界，不能仅因改变排序而阻断恢复。任一其余不一致都必须拒绝恢复并归档，不能静默采用当前工作区或当前模型改写旧状态。检查点是本地受保护的治理记录，保存恢复所需的冻结证据和已提交角色响应；它绝不保存凭据、原始工具参数或工具输出。

只有以下情况可以创建下一 epoch：存在开放问题、上一 epoch 取得新证据、或后续强制治理门禁尚未完成。重复搜索、被拒绝请求、提供商错误、无新证据循环和已完成阶段均不能触发续跑。

## 10. 状态转换

```text
阶段以初始额度开始
  -> 成功的新证据操作
  -> 协调器记录进展
  -> 到达软限制
       -> 有进展 + 必要工作未完成 + 受保护预算充足
            -> 授予有界批次并继续
       -> 否则拒绝续配，要求给出证据化结论
  -> 获得有效阶段回答
       -> 正常治理转换
  -> 在硬上限或项目截止前仍未获得有效回答
       -> 中止角色，REJECTED，并归档自适应预算账本
```

被拒绝的工具请求必须作为工具结果返回给角色，不能仅凭一次拒绝终止阶段；但该请求消耗反循环额度，且不能获得续配。

## 11. 实施计划

1. 在 `ansteel-discussion.ts` 定义策略类型、解析校验、默认值和不可变状态。
2. 扩展阶段审计，记录重复和被拒绝请求计数，同时继续脱敏参数和工具输出。
3. 在软限制处以协调器预算决定替换固定阶段工具检查，保留硬上限和项目截止时间。
4. 在任何可选续配前为后续强制治理阶段预留预算。
5. 将每个预算事件持久化至运行检查点和 Markdown 报告。
6. 将批处理执行拆分为可恢复 epoch，增加 `--ansteel-resume <run-id>` 和检查点状态机校验。
7. 实现本地 `pi --ansteel-supervise` 监督器：它以项目锁保护 `ready-to-resume` 检查点，只读取持久化状态决定续跑，并为每个 epoch 启动新的 CLI 子进程；锁必须在 `spawn` 前持久化 `starting` 声明，随后记录运行中子进程 PID，不能仅依赖父进程 PID 接管孤儿锁。前台子进程不得长期持有模型连接。外部调度器可以调用该命令，但不得绕过它直接猜测检查点状态。
8. 更新 `ansteel.md`，说明配置、恢复、保证和拒绝语义。
9. 添加确定性核心、CLI、检查点和恢复回归。

## 12. 测试矩阵

| 场景 | 必须结果 |
| --- | --- |
| 软超时前有新的成功证据操作 | 授予一次有界续配并记录 |
| 软超时前只有重复搜索 | 拒绝续配，记录重复惩罚 |
| 请求越界 `..` | 请求被拒绝，阶段保持存活，不获得续配信用 |
| 重复被拒绝请求 | 耗尽反循环额度，不再分配工具 |
| 初始阶段消耗可选额度 | 验证和会签的受保护预算仍可用 |
| 修订阶段有新证据且存在开放问题 | 受保护预算允许时获得有界批次 |
| 超时前没有新证据 | 在硬上限 fail-closed，并归档原因 |
| 提供商 402、429 或网络错误 | 不获得自适应资源，使用普通提供商失败分类 |
| 子目录 CLI Git 根审查 | 报告同时包含必需证据和自适应账本 |
| 最终会签拒绝 | 无论此前如何分配预算，都不显示独立 `## Tech Lead Consensus` |
| epoch 到达边界 | 写入 `ready-to-resume` 检查点，不将整体审查误报为完成 |
| 恢复时证据包哈希变化 | 拒绝恢复并归档配置/证据不一致原因 |
| 检查点后新增未入选的普通文件 | 从冻结路径清单重建原证据包，恢复继续，新增文件不进入本次审查证据 |
| 恢复时角色模型变化 | 拒绝恢复，除非检查点定义了已审计的替换流程 |
| 恢复时累计项目硬截止已过 | 不调用下一角色，写入 `expired` 检查点 |
| 数小时项目 SLA | 多个短 epoch 在累计截止前完成或以 `expired` 归档 |

## 13. 验收条件

功能只有在全部满足时才算完成：

1. 确定性 CLI 测试证明子目录 Git 根审查可授予或拒绝自适应额度，且不会丢失必需证据。
2. 每一次授予或拒绝均由协调器导出、不可变，并同时存在于报告和检查点。
3. 被拒绝、重复和提供商失败事件永远不能获得额外资源。
4. 可选初始调查不能耗尽验证与最终会签预留。
5. 未配置 `adaptiveBudgetPolicy` 时，固定预算行为保持不变。
6. 一个达到 epoch 边界的真实或确定性审查可由本地监督器在新进程中自动恢复，且不会重新执行已完成的治理状态转换；达到监督上限时保留可手动恢复的检查点而非伪造终态。
7. 一次真实三提供商审查至少展示一个自适应预算决定，并在配置项目截止时间内以可归档的治理结果结束。
