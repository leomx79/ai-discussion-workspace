# 循环讨论方案生成 — 重新设计工作流程

> 核心场景：用户给一个模糊问题，三个角色循环讨论，自动生成完整方案。
> 用户不需要给出细节，讨论本身产生细节。

---

## 一、你的真实需求

```
  你（用户）：
  "我有一个XXX问题，不知道该怎么处理"
  （给不出具体细节，不知道从哪里下手）

  你期望的效果：
  三个AI角色自己讨论2-3轮，
  最终输出一个完整的、可执行的方案，
  包含：问题分析、方案选择、实施步骤、风险预案、验证方法。

  而不是：
  你问一个具体问题 → AI回答 → 完事。
```

---

## 二、重新设计的工作流程（循环讨论）

### 旧流程（单轮验证，不适合你的需求）
```
  用户提问 → SE回答 → QA检查 → TL验证 → 输出
  （一轮就结束，适合事实核查）
```

### 新流程（多轮循环讨论，适合方案生成）
```
  用户给出模糊问题
       │
       ▼
  ┌─────────────────────────────────────────────────────┐
  │ 第1轮：发散                                         │
  │                                                     │
  │ TL：把模糊问题拆解成3-5个具体子问题                 │
  │ SE：针对每个子问题提出2-3个候选方案                 │
  │ QA：挑战每个方案——漏洞、风险、遗漏                  │
  │                                                     │
  │ 输出：候选方案列表 + 每个方案的问题                 │
  └────┬────────────────────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────────────────────────┐
  │ 第2轮：收敛                                         │
  │                                                     │
  │ SE：根据QA的质疑，淘汰弱方案，深化强方案            │
  │     补充：实施步骤、代码示例、配置细节              │
  │ QA：审查深化后的方案——可行性、完整性、边界情况      │
  │ TL：亲自验证关键技术假设（干部参加劳动）            │
  │                                                     │
  │ 输出：1-2个可行方案 + 详细实施步骤                  │
  └────┬────────────────────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────────────────────────┐
  │ 第3轮：定稿                                         │
  │                                                     │
  │ SE：输出最终方案（完整文档级）                      │
  │     包含：问题分析、方案、步骤、风险、验证          │
  │ QA：最终审查 + 补充风险预案和回滚方案               │
  │ TL：三方合议 + 裁决 + 签字                          │
  │                                                     │
  │ 输出：完整可执行方案                                │
  └─────────────────────────────────────────────────────┘
```

### 关键区别

| 维度 | 旧流程（单轮验证） | 新流程（循环讨论） |
|---|---|---|
| 用户输入 | 具体问题 | 模糊问题 |
| 讨论轮次 | 1轮 | 2-3轮 |
| SE的角色 | 回答问题 | **生成方案**（从无到有） |
| QA的角色 | 检查答案 | **挑战+补充**（让方案更完善） |
| TL的角色 | 验证答案 | **拆解问题+引导讨论+验证** |
| 输出 | 验证后的答案 | **完整可执行方案** |
| 细节来源 | 用户提供 | **讨论产生** |

## 三、每个角色在循环讨论中的具体工作

### 3.1 Tech Lead — 拆解问题 + 引导讨论

```
  第1轮（发散）：
  ├── 把用户的模糊问题拆解成具体子问题
  │   用户说："我的网站很慢"
  │   TL拆解：
  │   ① 是前端加载慢还是后端响应慢？
  │   ② 是所有页面慢还是特定页面？
  │   ③ 是最近才慢还是一直慢？
  │   ④ 服务器资源是否充足？
  │   ⑤ 有没有慢查询或N+1问题？
  │
  ├── 定义讨论边界和优先级
  └── 告诉SE："先针对①②④提方案，③⑤后续再说"

  第2轮（收敛）：
  ├── 亲自验证关键技术假设
  │   "SE说加Redis缓存能解决，让我验证一下当前有没有Redis..."
  ├── 引导讨论方向
  │   "QA指出缓存一致性问题很重要，SE请重点回应"
  └── 淘汰不可行方案

  第3轮（定稿）：
  ├── 主持三方合议
  ├── 做最终裁决
  └── 签字确认
```

### 3.2 Staff Engineer — 生成方案 + 逐步深化

```
  第1轮（发散）：
  ├── 针对TL拆解的每个子问题，提出2-3个候选方案
  │   子问题①"前端还是后端慢"：
  │   方案A：用Chrome DevTools分析前端加载瀑布图
  │   方案B：用APM工具（如Skywalking）分析后端链路
  │   方案C：直接看服务器日志和监控
  │
  ├── 每个方案标注：优缺点、适用场景、置信度
  └── 不确定的地方标L3/L4，不装懂

  第2轮（收敛）：
  ├── 根据QA质疑，淘汰弱方案
  │   "QA说方案C需要已有监控系统，我们还没有，淘汰"
  ├── 深化强方案
  │   补充：具体实施步骤、代码示例、配置方法
  │   补充：时间估算、依赖项、前置条件
  └── 回应QA的每个质疑（修正三要素）

  第3轮（定稿）：
  ├── 输出完整方案文档
  │   包含：问题分析、方案选择理由、实施步骤、
  │         代码示例、配置、风险预案、验证方法
  └── 标注每个断言的置信度
```

### 3.3 QA Engineer — 挑战 + 补充 + 完善

```
  第1轮（发散）：
  ├── 挑战每个候选方案
  │   "方案A：如果前端没问题，这个方案就白做了"
  │   "方案B：APM工具本身有性能开销，会不会让慢的更慢？"
  │   "方案C：你说看日志，但日志级别够吗？有慢查询日志吗？"
  │
  ├── 指出遗漏
  │   "你们都没考虑CDN的问题"
  │   "数据库连接池配置有没有检查？"
  │
  └── 提出补充方向
      "建议先做一个5分钟快速诊断，再决定深入方向"

  第2轮（收敛）：
  ├── 审查深化后的方案
  │   可行性：步骤能跑通吗？依赖项都有吗？
  │   完整性：边界情况考虑了吗？异常处理呢？
  │   风险：最坏情况是什么？有回滚方案吗？
  │
  └── 补充风险预案
      "如果加了缓存后数据不一致怎么办？"
      "如果优化后还是慢，下一步是什么？"

  第3轮（定稿）：
  ├── 最终审查
  ├── 补充：回滚方案、监控告警、验收标准
  └── Sign-off
```

## 四、循环讨论的实际示例

### 用户输入（模糊）
```
"我写了一个Python爬虫，但是经常被目标网站封IP，不知道怎么解决。"
```

### 第1轮：发散

**TL（拆解问题）：**
```
【角色】Tech Lead（干部）
【立项】用户的问题拆解为以下子问题：
  ① 封IP的原因是什么？（频率？请求头？行为模式？）
  ② 如何降低被封的概率？（限速？伪装？分散？）
  ③ 被封后怎么恢复？（IP池？自动切换？）
  ④ 有没有合规的替代方案？（官方API？）
讨论边界：仅讨论技术方案，不讨论绕过法律限制。
优先级：先①④，再②③。
```

**SE（提候选方案）：**
```
【角色】Staff Engineer（技术人员）
【方案】

子问题①：封IP原因分析
  方案A：分析请求日志，找出触发封禁的模式 [L2🟡]
    推理：大多数WAF基于频率+行为模式检测
  方案B：用浏览器手动访问对比，看是否有JS挑战 [L3🟠]
    不确定：不知道目标网站用什么反爬机制

子问题④：合规替代
  方案C：检查目标网站是否提供官方API [L2🟡]
    推理：很多网站有API，比爬虫稳定且合规
  方案D：使用公开数据集或第三方数据服务 [L3🟠]
    不确定：不知道具体是什么网站

子问题②：降低被封概率
  方案E：请求限速 + 随机延迟 [L2🟡]
  方案F：模拟浏览器请求头 + Session管理 [L2🟡]
  方案G：使用代理IP池 [L2🟡]
    排除：免费代理不稳定 [L4🔴 不确定]

子问题③：被封后恢复
  方案H：自动检测封禁 + 切换IP [L2🟡]
  方案I：指数退避重试 [L2🟡]

【替代方案对比】
  优先推荐：先查④（官方API），如果有API就不用爬虫了。
  次选：②（限速+伪装），成本最低。
  最后：③（IP池），成本最高但最可靠。
```

**QA（挑战）：**
```
【角色】QA Engineer（工人，有否决权）
【审查模式】黑盒审查
【审查结果】

方案A质疑：
  定位："分析请求日志，找出触发封禁的模式"
  问题：用户可能没有完整的请求日志
  风险：如果没有日志，这个方案无法执行
  建议：先确认用户是否有日志，没有的话先加日志

方案C质疑：
  定位："检查目标网站是否提供官方API"
  问题：没有说明怎么查（看文档？搜索？）
  建议：给出具体查找方法

方案G质疑：
  定位："使用代理IP池"
  问题：没有说明代理来源、成本、法律风险
  风险：某些代理可能涉及合规问题
  建议：补充合规性说明

遗漏：
  ❌ 没有考虑 robots.txt 合规性
  ❌ 没有考虑请求并发数控制
  ❌ 没有考虑 User-Agent 轮换
  ❌ 没有考虑 Cookie/Session 管理

【否决】❌
理由：方案不够完整，缺少合规性分析和具体实施细节。
```

### 第2轮：收敛

**SE（修正+深化）：**
```
【角色】Staff Engineer（技术人员）
【修正】

回应QA质疑：
  1. "用户可能没有日志" → 你说得对。
     修正：第一步先加请求日志（代码示例如下），再分析。
     置信度调整为 L1🟢（给出了具体代码）

  2. "没说明怎么查API" → 你说得对。
     修正：具体方法：① 搜索"网站名+API" ② 看网站footer
     ③ 查 developer.网站名.com ④ 搜索"网站名+developer"

  3. "代理合规问题" → 你说得对。
     修正：补充合规说明，建议用正规代理服务商。

  4. 遗漏补充：
     + robots.txt 检查（代码示例）
     + 并发控制（asyncio.Semaphore）
     + User-Agent 轮换（fake_useragent库）
     + Session 管理（requests.Session）

【深化后的推荐方案】

  第一步：合规检查（5分钟）
    - 检查 robots.txt
    - 搜索官方API
    - 如果有API → 直接用API，结束

  第二步：如果没有API，优化爬虫（1-2小时）
    - 加请求日志
    - 限速：每次请求间隔 2-5 秒（随机）
    - 模拟浏览器请求头
    - 使用 Session 保持连接
    - 并发控制：最多3个并发

  第三步：如果仍被封，加代理（2-4小时）
    - 使用正规代理服务商
    - 自动检测封禁（HTTP 403/429）
    - 自动切换IP
    - 指数退避重试

  代码示例：[具体Python代码]
```

**QA（重审）：**
```
【角色】QA Engineer（工人，有否决权）
【审查模式】灰盒审查（看了SE的代码示例）
【审查结果】

  第一步合规检查 → ✅ 完整
  第二步优化爬虫 → ✅ 步骤清晰，代码可执行
  第三步加代理 → ⚠️ 缺少"怎么判断被封了"的具体逻辑

  补充风险预案：
  - 如果代理也被封 → 降低频率到10秒/次
  - 如果网站改了结构 → 加异常处理，自动暂停
  - 如果数据不完整 → 加数据校验，记录缺失

【通过】✅（条件：TL验证代码可执行）
```

**TL（亲自验证）：**
```
【角色】Tech Lead（干部参加劳动）
【验证】

  我做了什么：执行了SE提供的代码示例
  我看到了什么：代码可以正常运行，限速和请求头模拟有效
  为什么这能证明：基本框架可行，具体效果取决于目标网站

  补充裁决：
  - 优先走第一步（合规检查），成本最低
  - 第二步是核心，必须做
  - 第三步按需，不要一上来就用代理

【裁决】同意SE的方案，QA的补充纳入最终方案。
```

### 第3轮：定稿

**SE（输出最终方案）→ QA（补充回滚+监控）→ TL（三方合议签字）**

最终输出：一份完整的、可执行的解决方案文档。

## 五、与旧流程的对比

```
  旧流程（你问→AI答）：
  用户："爬虫被封IP怎么办？"
  AI："你可以用代理IP、限速、模拟浏览器..."
  → 泛泛而谈，没有针对性，没有步骤，没有代码

  新流程（循环讨论）：
  用户："爬虫被封IP怎么办？"（同样模糊）
  TL：拆解成4个子问题
  SE：提出9个候选方案 + 代码
  QA：挑战 → 发现4个遗漏 → SE补充
  TL：亲自验证代码
  → 输出：3步方案 + 代码 + 风险预案 + 回滚方案
```
