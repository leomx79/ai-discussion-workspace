# 运行原理深度解析 — 鞍钢宪法式AI防幻觉讨论系统

> 本文档彻底讲清楚：它到底是什么、怎么运行、怎么通信、怎么质疑。
> 包括优势和局限，不回避问题。

---

## 一、它到底是什么？（诚实回答）

### 1.1 一句话回答

**Kilo Code 的自定义 Agent = 同一个大模型 + 不同的系统提示词（System Prompt）+ 共享的对话上下文。**

它**不是**多个独立的AI程序在各自运行。
它**是**同一个AI，戴上不同的"帽子"，按顺序发言。

### 1.2 类比

```
  ❌ 不是这样（真正的多智能体）：
  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │ 程序A    │  │ 程序B    │  │ 程序C    │
  │ 独立运行 │  │ 独立运行 │  │ 独立运行 │
  │ 独立内存 │  │ 独立内存 │  │ 独立内存 │
  │ 独立CPU  │  │ 独立CPU  │  │ 独立CPU  │
  └────┬─────┘  └────┬─────┘  └────┬─────┘
       │    消息传递   │    消息传递   │
       └──────────────┴──────────────┘

  ✅ 实际是这样（多角色/多人格）：
  ┌─────────────────────────────────────────┐
  │           同一个大模型（LLM）            │
  │                                         │
  │  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
  │  │TL帽子   │ │SE帽子   │ │QA帽子   │   │
  │  │(提示词A)│ │(提示词B)│ │(提示词C)│   │
  │  └─────────┘ └─────────┘ └─────────┘   │
  │                                         │
  │  共享对话上下文（所有发言都能看到）       │
  └─────────────────────────────────────────┘
```

### 1.3 那为什么还有效？

虽然是同一个模型，但**不同的系统提示词会让模型产生真正不同的"思维模式"**：

- 戴上 **TL帽子** → 模型倾向于验证、裁决、动手
- 戴上 **SE帽子** → 模型倾向于构建方案、标注置信度
- 戴上 **QA帽子** → 模型倾向于挑刺、质疑、找漏洞

这就像**同一个人扮演法官、律师、检察官**——虽然是同一个大脑，
但角色切换会激活不同的思维路径，比"一个人自说自话"好得多。

**关键：共享上下文让QA能看到SE说的每一句话，逐条质疑。**

### 2.2 核心技术要点

| 要点 | 说明 |
|---|---|
| **本质** | 同一个LLM的多次API调用，每次换不同的System Prompt |
| **通信方式** | 共享对话历史（后一个角色能看到前面所有角色说的话） |
| **角色切换** | 用户手动切换 或 协调器自动切换 |
| **记忆** | 单次对话内共享上下文；跨对话无记忆 |
| **工具调用** | 每个角色可以独立使用工具（搜索、执行命令、读文件） |
| **否决权** | 通过提示词约束（不是代码强制） |

## 三、角色之间怎么通信？

### 3.1 通信机制：共享对话上下文

```
  ┌─────────────────────────────────────────────────────┐
  │                  对话上下文（Context Window）         │
  │                                                     │
  │  ┌─────────────────────────────────────────────┐    │
  │  │ System Prompt（当前角色的提示词）            │    │
  │  │ + AGENTS.md + ansteel-constitution.md       │    │
  │  └─────────────────────────────────────────────┘    │
  │                                                     │
  │  ┌─────────────────────────────────────────────┐    │
  │  │ 对话历史（所有之前的发言）                   │    │
  │  │                                             │    │
  │  │ [TL]: 立项内容...                           │    │
  │  │ [SE]: 方案内容... ← QA能看到这些            │    │
  │  │ [QA]: 质疑内容... ← SE修正时能看到          │    │
  │  │ [SE]: 修正内容... ← TL验证时能看到          │    │
  │  │ [TL]: 验证结果...                           │    │
  │  └─────────────────────────────────────────────┘    │
  │                                                     │
  │  ┌─────────────────────────────────────────────┐    │
  │  │ 当前用户指令                                 │    │
  │  │ "请逐条审查以上方案"                         │    │
  │  └─────────────────────────────────────────────┘    │
  │                                                     │
  │  → 模型生成回复 → 追加到对话历史                    │
  └─────────────────────────────────────────────────────┘
```

**关键点：QA不需要"接收消息"——它直接看到SE说的每一句话。**
这就是共享上下文的优势：零通信开销，完整信息透明。

### 3.2 与真正多智能体系统的对比

| 维度 | 本方案（Kilo Code多角色） | 真正多智能体（CrewAI/AutoGen） |
|---|---|---|
| 运行方式 | 同一LLM，顺序调用 | 多个独立进程/线程 |
| 通信 | 共享对话历史 | 消息传递（Message Passing） |
| 内存 | 共享上下文窗口 | 各自独立内存 |
| 并行 | ❌ 顺序执行 | ✅ 可并行 |
| 独立性 | ⚠️ 同一模型 | ✅ 可用不同模型 |
| 上下文限制 | ⚠️ 受上下文窗口限制 | ✅ 各自独立窗口 |
| 复杂度 | ✅ 极简（改配置文件） | ❌ 需要编程 |
| 可靠性 | ⚠️ 提示词约束 | ✅ 代码强制 |

### 3.3 通信的局限和解决

**局限：上下文窗口有限**
- 如果讨论太长（7步×多轮修正），对话历史可能超出上下文窗口
- 早期发言可能被截断

**解决方法：**
1. 每步输出尽量精简（提示词中已要求结构化输出）
2. 协调器在每步结束时生成摘要，压缩历史
3. 关键结论写入文件（write_file），不依赖上下文记忆
4. 如果讨论过长，开新对话，把上一步结论作为输入

## 四、角色需不需要深刻理解项目？

### 4.1 回答：需要，但方式不同

```
  角色对项目的理解来源：

  ┌─────────────────────────────────────────────────────┐
  │ 1. AGENTS.md（项目级指令）                          │
  │    → 每次对话自动注入，所有角色都能看到              │
  │    → 包含：项目背景、技术栈、约束条件               │
  │                                                     │
  │ 2. .kilo/rules/（规则文件）                         │
  │    → 自动注入，定义讨论纪律                         │
  │                                                     │
  │ 3. 工具调用（主动读取）                             │
  │    → read_file：读取项目文件                        │
  │    → search_files：搜索代码                         │
  │    → execute_command：执行命令                      │
  │    → browser_action：查网页                         │
  │                                                     │
  │ 4. 对话上下文（被动接收）                           │
  │    → 前面角色提到的项目信息                         │
  └─────────────────────────────────────────────────────┘
```

### 4.2 怎么让角色理解项目？

**方法一：在AGENTS.md中写项目背景（推荐）**

```markdown
# AGENTS.md

## 项目背景
- 项目名称：XXX管理系统
- 技术栈：Python 3.12 + FastAPI + PostgreSQL + React 19
- 部署环境：Docker + K8s
- 关键约束：必须兼容IE11（别问为什么）

## 讨论范围
- 本次讨论聚焦：数据库选型
- 不考虑：前端框架变更
```

**方法二：让角色自己读文件**

在提示词中已经给了工具权限（read_file, search_files等），
角色可以主动读取项目文件来理解上下文。

例如 TL 在验证时可以：
```
"让我亲自验证一下..."
→ 调用 read_file 读取 requirements.txt
→ 调用 execute_command 执行 python --version
→ 调用 search_files 搜索 "distutils" 相关代码
```

**方法三：用户在提问时提供上下文**

```
"请讨论：我们的项目用Python 3.12 + FastAPI，
 现在需要选择任务队列方案（Celery vs ARQ vs Dramatiq），
 项目代码在 ./src/ 目录下。"
```

### 4.3 不同角色对项目的理解深度

| 角色 | 需要理解什么 | 怎么理解 |
|---|---|---|
| Tech Lead | 全局架构、技术约束、风险点 | 读AGENTS.md + 读关键文件 + 亲自验证 |
| Staff Engineer | 技术细节、实现方案、替代方案 | 读代码 + 搜索 + 推理 |
| QA Engineer | 方案中的漏洞、未验证的假设 | 读SE的发言 + 搜索验证 + 逻辑分析 |

## 五、怎么提出质疑？（QA的核心机制）

### 5.1 质疑的触发

QA的质疑**不是自发的**，而是由**提示词驱动**的：

```
  qa-engineer.md 的 System Prompt 中写了：

  "你是QA Engineer，拥有否决权。
   审查清单（每次审查必须覆盖）：
   - [ ] 每个事实性断言是否标注了置信度？
   - [ ] L1断言是否给出了具体来源？来源是否可验证？
   - [ ] L2断言是否说明了推理依据？推理是否合理？
   - [ ] 是否存在未标注置信度的事实性断言？
   - [ ] 是否存在逻辑跳跃或循环论证？
   - [ ] 是否存在过时信息？
   ..."
```

当QA角色被激活时，模型会：
1. 读取对话历史中SE的方案
2. 按照审查清单逐条检查
3. 对每个断言提出"证据在哪？来源是什么？能否验证？"
4. 发现问题 → 提出质疑 或 行使否决权

### 5.2 质疑的具体过程（示例）

```
SE的方案：
  "Python 3.12移除了distutils [L1🟢]
   替代方案是setuptools [L2🟡]
   迁移很简单，只需要pip install setuptools [L2🟡]"

QA看到后，按审查清单逐条检查：

  断言1："Python 3.12移除了distutils" [L1🟢]
  ├── 有来源吗？→ 没有给出具体URL或文档 ❌
  ├── L1要求可交叉验证 → 无法验证 ❌
  └── 质疑：请提供具体来源（PEP编号、官方文档URL）

  断言2："替代方案是setuptools" [L2🟡]
  ├── 有推理依据吗？→ 没有说明为什么是setuptools ❌
  ├── 有没有其他替代？→ 没有提及 ❌
  └── 质疑：setuptools是唯一替代吗？还有没有其他选择？

  断言3："迁移很简单" [L2🟡]
  ├── "很简单"是模糊表述 ❌（违反讨论纪律）
  ├── 没有说明具体步骤 ❌
  └── 质疑：具体怎么迁移？有哪些坑？

  结论：【否决】3条断言中2条缺乏来源，1条模糊表述
```

### 5.3 否决权的执行

**否决权是提示词约束，不是代码强制。**

```
  提示词中写了：
  "如果你认为方案存在未解决的幻觉风险，你可以否决。
   否决后，讨论必须回到修正环节。"

  实际执行：
  QA输出 "【否决】理由：..."
  → 用户看到否决 → 切换到SE → 输入"请回应QA的质疑"
  → 或者协调器自动检测"否决"关键词 → 自动切回SE

  ⚠️ 局限：如果模型"忘记"了否决权（提示词遵从度不够），
     可能不会真的否决。这取决于模型能力和提示词质量。
```

### 5.4 质疑的质量取决于什么？

| 因素 | 影响 | 优化方法 |
|---|---|---|
| 模型能力 | 强模型质疑更精准 | 用Claude Sonnet/Opus或GPT-4o |
| 提示词质量 | 审查清单越具体越好 | 已内置9条审查清单 |
| 上下文完整 | QA必须看到SE的完整方案 | 共享对话历史保证 |
| 工具使用 | QA可以搜索验证 | 已配置search_files等工具 |
| 用户监督 | 用户检查QA是否真的在质疑 | 看输出格式是否合规 |

## 六、优势与局限（诚实评估）

### 6.1 优势

```
  ✅ 零代码：写Markdown文件即可，不需要编程
  ✅ 零部署：不需要服务器、数据库、消息队列
  ✅ 即时可用：VS Code + Kilo Code，打开就用
  ✅ 工具调用：角色可以读文件、执行命令、搜索、上网
  ✅ 信息透明：共享上下文，QA能看到SE的每一句话
  ✅ 结构化输出：L1-L4标注 + 固定输出格式
  ✅ 500+模型：每个角色可以用不同模型
  ✅ 低成本：不需要额外基础设施
```

### 6.2 局限

```
  ⚠️ 不是真正的多智能体：同一个模型，不同提示词
  ⚠️ 顺序执行：不能并行讨论（一个说完下一个再说）
  ⚠️ 上下文窗口限制：讨论太长会丢失早期信息
  ⚠️ 否决权是"软约束"：提示词约束，不是代码强制
  ⚠️ 角色可能"串戏"：模型可能忘记自己的角色
  ⚠️ 无持久记忆：跨对话不记得上次讨论
  ⚠️ 依赖用户驱动：手动切换角色（除非用协调器）
```

### 6.3 如何缓解局限

| 局限 | 缓解方法 |
|---|---|
| 不是真正多智能体 | 用不同模型（不同"大脑"）→ 方式一配置 |
| 上下文窗口限制 | 每步输出精简 + 关键结论写入文件 |
| 否决权是软约束 | 提示词中强化 + 用户监督 + 未来用Cline SDK代码强制 |
| 角色串戏 | 输出格式强制（【角色】标签）+ 提示词反复强调 |
| 无持久记忆 | 讨论结果保存为Markdown文件，下次对话时读取 |
| 依赖用户驱动 | 用ansteel-orchestrator协调器自动执行 |

## 八、总结

```
  问：它是智能体吗？
  答：是"多角色"而非"多智能体"。同一个模型，不同提示词，共享上下文。
```
