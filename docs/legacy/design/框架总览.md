## 三、七步流程

```
  ┌─────────┐
  │ 用户提问 │
  └────┬────┘
       ▼
  ┌─────────────────────────────────────────────────────────┐
  │ 步骤1：立项                                             │
  │ 👤 Tech Lead（干部）                                    │
  │ 📋 定义问题、范围、约束条件                             │
  └────┬────────────────────────────────────────────────────┘
       ▼
  ┌─────────────────────────────────────────────────────────┐
  │ 步骤2：初步方案                                         │
  │ 👤 Staff Engineer（技术人员）                           │
  │ 📝 提出方案，每个断言标注 L1🟢 L2🟡 L3🟠 L4🔴          │
  └────┬────────────────────────────────────────────────────┘
       ▼
  ┌─────────────────────────────────────────────────────────┐
  │ 步骤3：质疑                                             │
  │ 👤 QA Engineer（工人，有否决权）                        │
  │ 🔍 逐条审查：来源？证据？逻辑？置信度标注完整？         │
  │ ⚖️ 通过 → 跳到步骤5                                    │
  │ ❌ 否决 → 进入步骤4                                     │
  └────┬────────────────────────────────────────────────────┘
       │ 否决
       ▼
  ┌─────────────────────────────────────────────────────────┐
  │ 步骤4：回应修正                                         │
  │ 👤 Staff Engineer（技术人员）                           │
  │ ✏️ 逐条回应质疑，修正方案                               │
  │ 🔄 回到步骤3重新审查（最多3轮）                         │
  └────┬────────────────────────────────────────────────────┘
       │ 通过
       ▼
  ┌─────────────────────────────────────────────────────────┐
  │ 步骤5：亲自验证                                         │
  │ 👤 Tech Lead（干部参加劳动）                            │
  │ 🔬 亲自动手：搜索、执行代码、查文档、跑测试             │
  │ 📊 输出验证报告                                         │
  └────┬────────────────────────────────────────────────────┘
       ▼
  ┌─────────────────────────────────────────────────────────┐
  │ 步骤6：三方合议                                         │
  │ 👤 TL + SE + QA 依次 Sign-off                           │
  │ ✅ 同意 / ❌ 反对（附理由）                              │
  │ ⚠️ 任何一方反对 → 回到相关步骤修正                      │
  └────┬────────────────────────────────────────────────────┘
       ▼
  ┌─────────────────────────────────────────────────────────┐
  │ 步骤7：输出归档                                         │
  │ 📦 最终结论 + 置信度标注 + 完整讨论记录                 │
  │ 💾 保存为 Markdown 文件                                  │
  └─────────────────────────────────────────────────────────┘
```

## 四、置信度标签体系

```
  ┌────────────────────────────────────────────────────────────┐
  │                    置信度标签（强制使用）                    │
  │                                                            │
  │  L1 🟢 已验证                                              │
  │  ├── 有明确来源（URL、文档、代码行号）                      │
  │  ├── 可交叉验证                                            │
  │  └── 例："Python 3.12移除了distutils [L1🟢]                │
  │           来源：docs.python.org/3.12/whatsnew/3.12.html"   │
  │                                                            │
  │  L2 🟡 高可信                                              │
  │  ├── 基于可靠知识，推理依据充分                             │
  │  ├── 无法即时验证但逻辑自洽                                │
  │  └── 例："微服务通常比单体部署更复杂 [L2🟡]                │
  │           推理：每个服务独立部署、网络通信开销"              │
  │                                                            │
  │  L3 🟠 待验证                                              │
  │  ├── 不确定，需要进一步核查                                │
  │  ├── 必须建议验证方法                                      │
  │  └── 例："React 19可能改变了use()的行为 [L3🟠]             │
  │           建议验证：查看react.dev官方文档"                  │
  │                                                            │
  │  L4 🔴 存疑/未知                                           │
  │  ├── 不确定或可能错误                                      │
  │  ├── 必须明确说"我不确定"                                  │
  │  └── 例："这个API的参数可能是X [L4🔴]                      │
  │           我不确定，需要查文档确认"                         │
  └────────────────────────────────────────────────────────────┘
```

## 五、角色制衡关系

```
                    ┌──────────────┐
                    │  Tech Lead   │
                    │   （干部）    │
                    │              │
                    │ • 亲自验证   │
                    │ • 主持合议   │
                    │ • 裁决争议   │
                    └──┬───────┬───┘
                       │       │
              裁决争议 │       │ 抽查验证
                       │       │
            ┌──────────▼─┐   ┌─▼──────────┐
            │   Staff    │   │     QA     │
            │ Engineer   │◄─►| Engineer   │
            │（技术人员）│   │ （工人）   │
            │            │   │            │
            │ • 提方案   │   │ • 逐条审查 │
            │ • 标L1-L4  │   │ • 行使质疑 │
            │ • 回应质疑 │   │ • 行使否决 │
            │ • 修正方案 │   │ • Sign-off │
            └────────────┘   └────────────┘
                  ▲                 │
                  │    否决→修正    │
                  └─────────────────┘

  制衡机制：
  • SE 提方案 → QA 审查（工人监督技术人员）
  • QA 否决 → SE 必须修正（工人有真实权力）
  • TL 亲自验证（干部不能只指挥不动手）
  • 三方 Sign-off（任何一方反对都不能通过）
```

## 九、防幻觉机制总结

```
  普通AI（马钢宪法/苏联模式）：
  ┌──────────────────────────────────────────┐
  │  一个大脑 → 直接输出 → 可能有幻觉       │
  │  "React 19的use()可以在条件语句中使用"   │
  │  （没有验证，没有质疑，没有来源）        │
  └──────────────────────────────────────────┘

  鞍钢宪法式AI（多角色制衡）：
  ┌──────────────────────────────────────────┐
  │  SE提出 → QA质疑 → SE修正 → TL验证      │
  │  → 三方合议 → 带来源的结论               │
  │                                          │
  │  "use()可以在条件语句中使用 [L1🟢]       │
  │   来源：react.dev/reference/react/use"   │
  │   （QA验证了来源，TL亲自确认了）         │
  └──────────────────────────────────────────┘

  5道防线：
  ① 置信度标注 → 强制区分"确定"和"不确定"
  ② QA质疑    → 找出没有来源的断言
  ③ QA否决    → 阻止未验证的结论通过
  ④ TL验证    → 干部亲自动手确认
  ⑤ 三方合议  → 任何一方反对都不通过
```
