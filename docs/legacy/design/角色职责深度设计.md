# 角色职责深度设计 — 谁需要理解什么、怎么让别人理解自己

> 解决三个核心问题：
> 1. 角色需不需要完整了解项目？
> 2. QA需不需要理解代码？
> 3. 执行者怎么让其他人理解自己为什么这么做？

---

## 一、核心原则：不是所有人都需要理解一切

### 1.1 真实公司的做法

在 Google / OpenAI 的真实团队中：

| 角色 | 需要理解什么 | 不需要理解什么 |
|---|---|---|
| Tech Lead | 全局架构、技术风险、团队能力 | 每行代码的细节 |
| Staff Engineer | 自己负责模块的每个细节 | 其他模块的实现细节 |
| QA Engineer | 代码**应该做什么**（规格）+ 关键路径的实现 | 所有代码的每行逻辑 |
| Product Manager | 用户需求、业务目标 | 技术实现细节 |

**关键：每个人理解自己职责范围内的东西，通过"接口"与其他人协作。**

### 1.2 映射到AI讨论

```
  ❌ 错误做法：每个角色都读全部代码、理解全部上下文
     → 浪费上下文窗口，角色"串戏"，讨论失焦

  ✅ 正确做法：每个角色理解自己需要的部分
     → TL理解全局 → 用"立项简报"告诉其他人该关注什么
     → SE理解技术细节 → 用"方案+L1-L4"告诉其他人自己做了什么
     → QA理解"应该是什么样" → 用"审查清单"检查SE的输出
```

## 二、每个角色需要理解什么（重新设计）

### 2.1 Tech Lead（干部）— 理解全局

```
  必须理解：
  ├── 项目目标：这个项目要解决什么问题？
  ├── 技术架构：整体架构是什么？关键组件有哪些？
  ├── 约束条件：性能要求、兼容性、安全要求
  ├── 风险点：哪里最容易出错？哪里有过历史问题？
  └── 团队能力：SE擅长什么？QA的关注点是什么？

  不需要理解：
  ├── 每行代码的具体实现
  ├── 每个函数的参数细节
  └── 第三方库的内部实现

  怎么获取理解：
  ├── 读 AGENTS.md（项目背景）
  ├── 读关键文件（README、架构文档、配置文件）
  ├── 执行命令验证环境（python --version, pip list）
  └── 用户提问时提供的上下文

  怎么让别人理解自己：
  ├── 立项简报：用3-5句话说清楚"我们要讨论什么、为什么、边界在哪"
  ├── 验证报告：不只说"验证通过"，要说"我做了什么、看到了什么、为什么这能证明"
  └── 裁决理由：不只说"我同意SE"，要说"因为证据X，所以结论Y"
```

### 2.2 Staff Engineer（技术人员）— 理解技术细节

```
  必须理解：
  ├── 当前任务的技术细节：要改什么、怎么改、影响什么
  ├── 相关代码的实现：自己负责模块的代码逻辑
  ├── 替代方案：有哪些选择？各自优缺点？
  ├── 依赖关系：改动会影响哪些上下游？
  └── 已知限制：哪些是确定的、哪些是不确定的

  不需要理解：
  ├── 项目的全局业务逻辑（那是TL和PM的事）
  ├── 测试策略的细节（那是QA的事）
  └── 其他模块的实现细节（除非有依赖）

  怎么获取理解：
  ├── 读 TL 的立项简报（知道要做什么）
  ├── 读相关代码文件（read_file, search_files）
  ├── 执行命令验证假设（execute_command）
  ├── 搜索文档和资料（browser_action）
  └── 读 QA 的质疑（知道哪里需要补充）

  怎么让别人理解自己（最重要！）：
  ├── 方案说明：不只说"用X方案"，要说"因为A原因，所以选X，不选Y是因为B"
  ├── 置信度标注：L1-L4 不只是标签，是"我对这句话有多确定"
  ├── 推理链：每个结论都要有"因为...所以..."的推理过程
  ├── 不确定性声明：不确定的地方必须明确说"这里我不确定，因为..."
  └── 修正说明：被QA质疑后，不只改答案，要说"你指出得对，我之前错了，因为..."
```

### 2.3 QA Engineer（工人）— 理解"应该是什么样"

```
  必须理解：
  ├── 规格/预期：代码应该做什么？正确的行为是什么？
  ├── SE的方案逻辑：SE说的推理链是否自洽？
  ├── 关键路径：哪些断言如果错了，后果最严重？
  ├── 常见幻觉模式：AI容易在哪些地方犯错？
  │   ├── 编造不存在的API/函数
  │   ├── 混淆不同版本的行为
  │   ├── 把"可能"说成"确定"
  │   ├── 过时信息（训练数据截止日期）
  │   └── 混淆不同来源的信息
  └── 验证方法：怎么证明一个断言是对是错？

  不需要理解：
  ├── 代码的每行实现（不是做代码审查）
  ├── 为什么选择这个技术方案（那是SE和TL的事）
  ├── 项目的商业目标（那是PM的事）
  └── 如何修复问题（那是SE的事，QA只负责发现）

  怎么获取理解：
  ├── 读 TL 的立项简报（知道"正确"的标准是什么）
  ├── 读 SE 的方案（逐条检查）
  ├── 搜索验证（browser_action 查官方文档）
  ├── 执行验证（execute_command 跑代码确认）
  └── 读 TL 的验证报告（交叉验证）

  怎么让别人理解自己：
  ├── 质疑必须具体：不只说"这不对"，要说"第3条断言说X，但根据Y来源，实际是Z"
  ├── 否决必须给理由：不只说"否决"，要说"因为断言A缺乏来源，断言B与事实矛盾"
  ├── 通过也要给理由：不只说"通过"，要说"5条断言中4条有L1来源，1条L2推理合理"
  └── 建议验证方法：质疑时不只说"需要验证"，要说"建议执行XX命令/查看XX文档"
```

## 三、"怎么让别人理解自己"— 透明决策机制

### 3.1 问题：为什么需要透明？

```
  不透明的讨论：
  SE: "用方案A。"
  QA: "不对。"
  SE: "那用方案B。"
  TL: "行，就B吧。"
  → 没人知道为什么选B，下次遇到类似问题还要重新讨论

  透明的讨论：
  SE: "用方案A，因为性能更好 [L2🟡]，推理：A的时间复杂度O(n)，B是O(n²)"
  QA: "质疑：你说A是O(n)，但A的内部实现用了排序，实际是O(nlogn) [L1🟢 来源：源码第42行]"
  SE: "你说得对，我忽略了内部排序。修正：A是O(nlogn)，但仍优于B的O(n²)"
  TL: "验证确认。选A，因为即使O(nlogn)也优于B。裁决依据：QA的源码验证。"
  → 每个人都知道为什么选A，决策可追溯
```

### 3.2 透明决策的三个层次

```
  层次1：结论透明（最基本）
  ├── 每个断言标注 L1-L4
  ├── 每个结论有明确表述
  └── 已实现 ✅

  层次2：推理透明（关键）
  ├── 每个结论有"因为...所以..."的推理链
  ├── 每个选择有"选X不选Y，因为..."的对比
  ├── 每个修正有"之前错了，因为...现在改为..."的说明
  └── 需要在提示词中强化 ⚠️

  层次3：验证透明（最严格）
  ├── 每个验证有"我做了什么、看到了什么、为什么这能证明"
  ├── 每个来源有具体URL/文件路径/行号
  ├── 每个否决有"哪条断言、什么问题、为什么有风险"
  └── 需要在提示词中强化 ⚠️
```

### 3.3 每个角色的"让别人理解"清单

**TL 必须说清楚的：**
- [ ] 为什么讨论这个问题？（立项理由）
- [ ] 讨论的边界在哪？（不讨论什么）
- [ ] 我验证了什么？怎么验证的？结果是什么？（验证三要素）
- [ ] 我为什么这么裁决？证据是什么？（裁决依据）

**SE 必须说清楚的：**
- [ ] 我为什么选这个方案？（选择理由）
- [ ] 我为什么不选其他方案？（排除理由）
- [ ] 这个断言我有多确定？为什么？（置信度+推理）
- [ ] 被质疑后，我错在哪？为什么错？怎么改？（修正三要素）

**QA 必须说清楚的：**
- [ ] 我质疑的是哪条断言？（定位）
- [ ] 问题是什么？（具体问题）
- [ ] 为什么这是问题？（风险分析）
- [ ] 建议怎么验证？（验证方法）
- [ ] 我为什么否决/通过？（决策依据）

## 四、QA 到底需不需要理解代码？

### 4.1 回答：需要理解"应该做什么"，不需要理解"怎么做的"

```
  QA 需要理解的（规格层）：
  ├── 这个函数应该返回什么？
  ├── 这个API的正确行为是什么？
  ├── 边界条件是什么？（空输入、极大值、并发）
  ├── 错误处理应该怎样？
  └── 性能预期是什么？

  QA 不需要理解的（实现层）：
  ├── 函数内部用了什么算法
  ├── 变量的命名和类型
  ├── 代码风格和结构
  └── 第三方库的内部实现

  例外：当 QA 需要验证 SE 的断言时，可能需要读代码
  例如：SE说"这个函数是O(n)"，QA需要看代码确认是否有隐藏循环
```

### 4.2 QA 的三种审查模式

```
  模式1：黑盒审查（最常用）
  ├── 只看 SE 的方案文本
  ├── 检查：置信度标注完整吗？来源可验证吗？逻辑自洽吗？
  ├── 不需要读代码
  └── 适合：方案评估、技术选型、概念辨析

  模式2：灰盒审查（需要验证时）
  ├── 读关键代码文件，验证 SE 的断言
  ├── 检查：SE说"这个API返回X"，实际代码是不是返回X？
  ├── 需要 read_file + search_files
  └── 适合：代码修改方案、Bug修复方案

  模式3：白盒审查（深度验证）
  ├── 执行代码，观察实际行为
  ├── 检查：SE说"性能是O(n)"，实际跑一下是不是？
  ├── 需要 execute_command + browser_action
  └── 适合：性能优化、安全审计、关键路径验证
```

## 五、改进后的角色提示词（核心变更）

### 5.1 Tech Lead 新增

```markdown
## 透明决策要求（必须遵守）

### 立项时必须说清楚
- 为什么讨论这个问题？（1-2句）
- 讨论的边界：讨论什么、不讨论什么
- 验收标准：什么算"讨论完成"

### 验证时必须说清楚（验证三要素）
- 我做了什么：具体执行的命令/搜索/文件读取
- 我看到了什么：实际输出/结果
- 为什么这能证明：结果如何支持/反驳断言

### 裁决时必须说清楚
- 裁决结果：同意/反对/修正
- 证据引用：基于哪条证据（引用SE/QA的具体发言）
- 推理过程：因为X证据，所以Y结论
```

### 5.2 Staff Engineer 新增

```markdown
## 透明决策要求（必须遵守）

### 提方案时必须说清楚
- 选择理由：为什么选这个方案（不是因为"我觉得好"）
- 排除理由：为什么不选其他方案（至少提一个替代并说明为什么不选）
- 推理链：每个结论都要有"因为...所以..."

### 被质疑时必须说清楚（修正三要素）
- 我错在哪：具体哪条断言有问题
- 为什么错：是知识错误、推理错误、还是信息不完整
- 怎么改：修正后的表述 + 新的置信度

### 不确定时必须说清楚
- 不确定的具体内容
- 不确定的原因（知识截止？无法验证？信息矛盾？）
- 建议的验证方法
```

### 5.3 QA Engineer 新增

```markdown
## 透明决策要求（必须遵守）

### 质疑时必须说清楚（质疑四要素）
- 定位：质疑的是哪条断言（引用原文）
- 问题：具体什么问题（缺来源？逻辑错误？过时？）
- 风险：如果这条断言是错的，后果是什么
- 建议：怎么验证（执行什么命令/查什么文档）

### 否决时必须说清楚
- 否决的具体断言（不是"整体不行"）
- 每个否决理由的证据
- 修正方向建议（不是让SE猜）

### 通过时也要说清楚
- 审查了哪些断言
- 每条的审查结果
- 为什么认为可以通过
```

## 六、信息流设计（谁在什么时候知道什么）

```
  步骤1 立项：
  TL → 所有人：项目背景、问题定义、讨论边界
  （SE和QA通过读TL的立项简报获取上下文）

  步骤2 方案：
  SE → 所有人：方案 + 选择理由 + L1-L4标注
  （QA通过读SE的方案获取审查对象）

  步骤3 质疑：
  QA → SE：质疑 + 具体问题 + 验证建议
  QA → TL：审查报告（通过/否决）
  （SE通过读QA的质疑知道哪里需要修正）

  步骤4 修正：
  SE → QA：修正 + 错在哪 + 为什么错 + 怎么改
  （QA通过读SE的修正知道问题是否解决）

  步骤5 验证：
  TL → 所有人：验证报告（做了什么、看到什么、证明什么）
  （SE和QA通过读TL的验证报告获得最终确认）

  步骤6 合议：
  所有人 → 所有人：Sign-off + 理由
  （每个人都知道其他人为什么同意/反对）

  步骤7 归档：
  TL → 文件：完整记录（结论+推理+验证+讨论）
  （未来任何人读这个文件都能理解决策过程）
```

## 七、总结

```
  问：角色需不需要完整了解项目？
  答：不需要。TL了解全局，SE了解技术细节，QA了解"应该是什么样"。
      通过"立项简报"和"方案说明"传递必要上下文。

  问：QA需不需要理解代码？
  答：需要理解"应该做什么"（规格），不需要理解"怎么做的"（实现）。
      但验证SE的断言时，可能需要读代码（灰盒/白盒审查）。

  问：执行者怎么让别人理解自己？
  答：三层透明——
      ① 结论透明：L1-L4标注（已有）
      ② 推理透明：因为...所以...（需强化）
      ③ 验证透明：做了什么、看到什么、证明什么（需强化）

  核心改进：每个角色的提示词增加"透明决策要求"，
  强制输出推理链、选择理由、修正说明、验证三要素。
```
